# Этап 1 — что сделано и что проверить (25.09.2026)

Сайт: https://dimitorius.github.io/delivery-pulse/

## Что есть

- **Модель событий** (`src/domain/`): канонические сущности из SPEC §4 (WorkItem, StatusTransition + маппинг статусов на категории, Iteration, DependencyLink, MergeRequest, PipelineRun, Deployment, Incident; Risk/Milestone/Survey/Cost/Annotation/MetricDefinitionChange описаны типами, но пока не симулируются). Журнал событий только дополняется (append-only); проекция `store.ts` собирает из него сущности. Метрики читают только проекцию, поэтому будущий адаптер Jira заменит только источник событий.
- **Симулятор** (`src/sim/`): дискретно-событийная модель программы Commerce Platform: Checkout, Payments и Catalog & Search на Scrum, Merchant Onboarding на Kanban, Platform на Scrum (у Platform есть зависимости от stream-команд). В модели есть разработчики, ревью, ёмкость QA, CI на main, деплои, инциденты, планирование спринтов и PI, межкомандные зависимости, незапланированная работа и сбежавшие в прод баги. Seed фиксирован, поэтому у всех одна и та же история. Результат не зависит от шага часов: тест это проверяет, и живой хвост на 1×/10×/100× даёт те же события.
- **История**: 3 PI по 10 недель (4 итерации + 1 IP), ~7 месяцев, 30 марта → 26 октября 2026; дальше живой хвост с планирования PI 4 (1× = 1 рабочий час в секунду). Работает в Web Worker. *(после ревью)*
- **17 метрик**, каждая вычисляется из событий, у каждой есть эталонный тест с ручным расчётом (`src/metrics/reference.test.ts`). Метаданные лежат в `registry/metrics/*.yaml` (определение, формула, события-источники, цель, бенчмарк, источники, флаги ⚠).
  - Lagging: Throughput, Cycle Time P85, Lead Time for Changes P50, Deployment Frequency, Change Failure Rate, Failed Deployment Recovery Time P50, Say/Do.
  - Current: WIP, Flow Efficiency, Blocked Items, PR Pickup P50, Main Build Success.
  - Leading: Net Flow, Aging WIP over SLE, Overdue Dependencies, Unplanned Work.
  - Строка «успеваем?»: PI Forecast (Monte Carlo When).
- **Сигналы**: XmR (правило 1: точка за пределами; правило «8 подряд по одну сторону»), Aging WIP против SLE, просроченные зависимости.
- **Экран Pulse**: шапка (уровень Program/команда, часы симуляции, скорость, счётчик сигналов; Inject scenario пока неактивна — это этап 3) → строка «успеваем?» → 3 колонки → справа сигналы и лента событий → мини-граф зависимостей. Клик по плитке открывает карточку: значение, цель, бенчмарк с источниками, формула, события-источники, тренд, XmR, распределение, разбивка по командам, все исходные записи.
- **Калибровка** (`src/sim/calibration.test.ts`): elite-профиль из SPEC §3 проверяется тестами. DORA: несколько деплоев в день, LT < 1 дня, CFR 3–5 %, recovery < 1 ч. Cycle time P85 ≈ 7 д с толстым хвостом, flow efficiency ≈ 35 %, Say-Do 80–90 %, цель спринта ≈ 85 %, carry-over < 15 %, main green > 95 %, flaky < 2 %, unplanned 13–20 %, инвестиции ≈ 60/20/20, закон Литтла. `npm run calibrate` печатает все значения.

## Решения, принятые при реализации (на твой просмотр)

Спецификацию эти решения не меняют, они уточняют то, что в ней не было задано.

1. **Перцентили — метод nearest rank** (сортировка, элемент ⌈p·n⌉). Любое значение можно проверить руками, формула показана в карточке.
2. **Точка старта cycle time** — первый вход в In Progress. Статус «To Do» (выбрано в спринт) — ещё до обязательства. Время считается календарное, выходные входят, как в Jira.
3. **Deployment Frequency** = регулярные деплои / рабочие дни / число сервисов в выборке. Так значение сравнимо между командой и программой. Rollback не считается.
4. **CFR**: знаменатель — регулярные деплои, «сбой» — деплой, на который ссылается инцидент.
5. **Flow Efficiency** = Σ активного времени / Σ cycle time (отношение сумм). Время в блокировке считается ожиданием даже в активном статусе.
6. **Net Flow** = прибыло − ушло в неделю, плюс = WIP растёт. ⚠ В разных источниках знак противоположный.
7. **XmR — робастный вариант Уилера**: центр — медиана, пределы — ±3,145 × медиана скользящего размаха. База — 12 недель *до* последних 8, чтобы недавний сдвиг не утащил центр за собой.
8. **Monte Carlo PI — по командам совместно** *(уточнено после ревью, см. ниже)*: PI готов, когда готова последняя команда. Если объединить throughput всех команд, получалось 100 % при ~60 % у каждой команды. Прогноз строится только по **committed**-объёму; в модель добавлены SAFe uncommitted (stretch) objectives (`piStretch`). (До ревью на конец истории было ≈ 64%; после ревью база elite — 91,7%.)
9. ~~PI = 8 недель = 4 спринта~~ → по ревью: **PI = 4 итерации + 1 IP = 10 недель**.
10. **Календарь**: UTC, пн–пт 09:00–17:00, без праздников.
11. **Цель спринта** — до 3 историй «главной» фичи спринта (у которой больше всего историй в спринте). Цель достигнута, если все они Done к концу спринта.
12. **Цели (targets) масштабируются по командам** там, где это счётчик (Blocked, Aging WIP, Net Flow): «≤ 1 на команду» → для программы ≤ 5.

## ⚠ Требовали твоего решения (контент) — решено, см. «Решения Дмитрия»

- **DORA-бенчмарки** (LT, DF, CFR, FDRT): первичный источник один — исследовательская программа DORA (отчёты 2023/2024). RedMonk и другие только пересказывают, независимых первичных источников нет.
- **Flow Efficiency 5–15 %** «типично» — цифра Kanban University. Данные ASOS её оспаривают. Помечено как спорное.
- **Say/Do 80–90 %** — практическая конвенция, первичного бенчмарка не нашёл (в Scrum Guide есть только Sprint Goal).
- **PR Pickup < 4 ч, Main green > 95 %, Unplanned 15–20 %** — есть только вендорские данные либо ничего. Оставлены как цели команды, не как бенчмарк.
- **Blocked, Overdue deps** — практика описана в одном источнике, пороги наши.
- URL книг Vacanti ведут на Leanpub/Goodreads, год WWIBD — 2018 по данным поиска. Стоит проверить.

## Решения Дмитрия (ревью 25.09.2026) и как они внесены

**Правки**

1. **Базовая линия — elite.** Commitment PI = 80% ёмкости под фичи; ёмкость = velocity × 4 dev-итерации − доля техдолга − резерв на незапланированное. Прогноз на конец истории — **91,7%**, весь живой PI 4 держится в 87–100%, все плитки на конец истории зелёные. Blocked now = 4 при цели ≤ 5.
   - Прогноз Monte Carlo по командам очень «крутой» (узкое распределение): при запасе чуть меньше он проваливается до 8–30% посреди PI без всяких сценариев. Поэтому сделано так:
     - пропускная способность берётся **недельными блоками** за **30 рабочих дней**, IP-дни исключены. Недельные блоки сохраняют автокорреляцию, и разброс не занижается;
     - seed выбран скриптом `scripts/seed-search.ts` по всем критериям elite (seed **399**). Эти критерии проверяют калибровочные тесты и `npm run baseline`.
   - По дороге найдены и исправлены два бага симулятора:
     - истории, добавленные в PI по ходу (рост scope), вставали за roadmap и до них не доходили руки;
     - незапланированная задача, перенесённая в следующий спринт, могла попасть в работу дважды.
2. **Signals ≠ Watch items.** Signals и счётчик в шапке — только XmR-сигналы и плитки со статусом «Off target». Отдельные задачи старше SLE и просроченные зависимости — в списке **Watch items**. Тест проверяет, что сигналы по целям совпадают с красными плитками.
3. **Low confidence при n < 10.** Для выборочных метрик (перцентили и доли) в YAML задано `minSample: 10`. Ниже порога плитка серая и подписана «low confidence · n=8 < 10».
4. **Say/Do — коридор 80–90%.** Ниже 70% — красный, в остальных случаях вне коридора — «Near limit». Если все 3 последних спринта команды > 95%, появляется пометка «possible sandbagging: CHK». Выборка n = committed-задачи с очками.
5. **PI = 4 + 1 IP = 10 недель, история = 3 PI (~7 мес.).**
   - В IP-итерации commitment легче (60% velocity, половина — инновационные спайки).
   - Velocity считается только по dev-итерациям, иначе IP занижала бы её.
   - Committed-объём PI планируется на 4 dev-итерации, а IP служит буфером.
6. **Гистерезис.** Статус меняется только после 3 обновлений подряд за порогом (`src/app/hysteresis.ts`, с тестами). Один и тот же стабилизированный статус видят плитка, счётчик и карточка.
7. **Net Flow** подписан «Net flow · arrived − finished», в плитке показаны оба числа.

**Решения по ⚠**

8. **DORA** (LT, DF, CFR, FDRT): подпись «DORA 2024 performance clusters» и примечание, что в DORA 2025 кластеры elite/high/medium/low заменены семью архетипами команд.
   - Источники: [отчёт DORA 2025 (Google Cloud)](https://cloud.google.com/resources/content/2025-dora-ai-assisted-software-development-report), [RedMonk](https://redmonk.com/rstephens/2025/12/18/dora2025/), [Agility at Scale](https://agility-at-scale.com/safe/ai-enabled-safe/dora-2025-for-ai-teams-seven-archetypes-every-safe-rte-should-know/).
   - ⚠ Сверить с dora.dev из этой среды не удалось: прокси блокирует dora.dev, redmonk.com и medium.com. Замена кластеров архетипами подтверждена по анонсу Google Cloud и пересказам (Scrum.org, Faros, Splunk).
9. **Flow efficiency** — тип «disputed»: две позиции рядом, Kanban University (5–15%) и данные ASOS (60+ команд, 2023). Чисел ASOS в карточке нет, только ссылка: сама статья из этой среды не открылась.
10. **Say/Do, PR pickup, Main green, Unplanned** — тип «Team goal, not a benchmark». Вендорские данные не показываются; если появятся, то только с подписью «vendor dataset».
11. **Blocked, Overdue deps** — «Our threshold (team-set / program-set)».
12. **Vacanti «When Will It Be Done?»** — печатное издание 2020, ISBN 9780986436376; ссылки на Leanpub и Amazon.
13. Все 12 решений реализации приняты.

## Как проверить самому

- Открыть сайт → кликнуть любую плитку → в карточке формула и таблица исходных записей.
- Переключить уровень на команду → перцентили пересчитываются по выборке команды (не усредняются).
- Включить 100× → через ~10 секунд проходит несколько недель, сигналы и прогноз меняются.
- `npm run baseline` — статусы всех плиток на конец истории и по дням живого PI 4.
