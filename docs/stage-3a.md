# Этап 3a — экраны Catalog, Library, Learn, Diagnose (01.10.2026)

Сайт: https://dimitorius.github.io/delivery-pulse/ · симулятор не менялся (seed 83, живой хвост PI 4–14 тот же).

## Что есть

1. **Catalog** (`#/catalog`): все 174 метрики из `content/catalog.yaml`.
   - Фильтры: домен, tier, статус (live / featured / synthetic / view / anti), уровень (lagging / current / leading), источник. Есть поиск по названию, вопросу и названиям во фреймворках.
   - Чипы «also known as» берутся из `aliases`: ≡ — сплошная рамка, ≈ — пунктирная, расхождение показывается во всплывающей подсказке.
   - Клик по строке открывает страницу метрики. У живой метрики это прежняя страница, к которой добавлены tier, чипы, карточка Learn и связанные симптомы. У остальных — страница каталога: синтетический ряд, график или пояснение.
2. **Library** (`#/library`): включает и выключает метрики и симптомы поверх реестра.
   - Хранится в браузере (IndexedDB), сохраняются только отличия от умолчаний. Есть экспорт и импорт JSON и сброс к умолчаниям.
   - Умолчания: live и featured включены, synthetic выключены. Из view включены CFD и scatterplot (они и раньше были на Flow), остальные выключены. Все симптомы включены.
   - Включённая синтетическая метрика появляется плиткой на своей вкладке, включённый view — графиком.
   - Выключенная живая метрика пропадает везде: с вкладки, с Pulse, из сигналов и Watch items.
   - Anti-метрики не переключаются: они остаются только в каталоге и Learn.
3. **Синтетика** — 102 ряда (100 synthetic + 2 featured: SAFe Competency, DevOps Health Radar).
   - Плитки с бейджем SYNTHETIC, пунктирной рамкой, без цели и без цвета. Подпись: «in production: an engineer survey / finance systems / …» (из поля `source`).
   - Ряд генерируется в браузере из собственного RNG-потока на каждую пару (метрика, команда). Seed потока = FNV-хэш от (seed 83, id, команда). Розыгрыши симулятора не затрагиваются, и тест это проверяет: журнал событий одинаковый с синтетикой и без неё.
   - Значение программы: для счётчиков — сумма по командам, для остального — медиана. Опросные метрики обновляются раз в месяц, квартальные — раз в 13 недель. OKR progress растёт внутри квартала и сбрасывается в начале следующего.
   - Status view → свой график, всё считается из событий:
     - CFD и scatterplot (вынесены из Flow);
     - Sprint burndown и Sprint burn-up (текущий спринт);
     - Risk burndown (та же формула, что у плитки Risk Exposure, по неделям);
     - Burn-up forecast (committed-истории PI и линии P85/P15 недельной пропускной способности).
4. **Learn** (`#/learn`, `#/learn/<id>`):
   - Tier 1–4 — раскрывающиеся секции (по умолчанию открыта Tier 1), у каждой метрики пометка «article» или «article coming».
   - Пути по ролям (DM / TPM / PjM) строятся из поля `roles` статей.
   - Статья:
     - флаги ⚠ — сверху;
     - answers, use / avoid;
     - секции в порядке из README;
     - калькулятор внутри «How it's calculated»;
     - «Read together with» с живыми мини-плитками;
     - кликабельные источники с датой проверки.
   - Где статьи нет — «Article coming», без текста.
   - Калькуляторы есть только у трёх статей с полем `calculator`: cycle-percentiles, say-do, monte-carlo. По умолчанию в них подставлены разобранные примеры из статей.
   - В боковой карточке живой метрики показываются answers, первый абзац «Why it exists», строка формулы и «Say it in an interview» (как в README).
5. **Diagnose** (`#/diagnose`, `#/diagnose/<id>`): 42 симптома по группам. Карточка симптома из `content/symptoms/<id>.md` содержит:
   - sounds like;
   - What is going on;
   - early и confirming signals с живыми мини-плитками и подписью «look for»;
   - гипотезы с проверкой;
   - плейбук (now / next sprints / watch after);
   - антипаттерны;
   - evidence с источниками.

   Где файла нет — «Playbook coming». Кнопка Inject scenario не тронута (этап 3b); на карточке написано только имя сценария.
6. **Scale**: сверху группа «SAFe flow metrics» — Flow Distribution, Flow Velocity, Flow Time ≈, Flow Load, Flow Efficiency, Flow Predictability.
   - Это те же определения из реестра (Throughput, Lead Time, WIP, Flow Efficiency, Flow Distribution, PI Predictability). Имя берётся из `aka.safe`, поэтому вычисления не дублируются.
   - Клик открывает ту же страницу метрики. Плитка PI Predictability на Scale больше не показывается дважды.
7. **Источники**: `content/sources.yaml` влит в `registry/sources.yaml`.
   - Добавлены 8 новых ключей.
   - У существующих появились поля `checked` и `note`.
   - Vacanti WWIBD — год 2020, полное название книги.
   - Тест сверяет каждый ключ контента с реестром: URL, дата проверки, год.

Тесты: 244, все зелёные (новый файл `src/content/content.test.ts`, 26 тестов). Сборка проходит.

## Решения при реализации (на твой просмотр)

1. **Разные id у живых метрик.** У 9 живых метрик id в каталоге и в реестре не совпадают (`queue-size-by-stage` → `queue-size`, `flaky-test-rate` → `flaky-rate`, `pipeline-duration-p95` → `pipeline-duration` и т. д.). По README «registry wins». Файлы `content/` я **не правил**: соответствие задано таблицей в коде (`CATALOG_TO_REGISTRY`), поэтому Cowork может писать в симптомах и статьях любой из двух id. Если хочешь, чтобы каталог переименовал Cowork, — таблица просто перестанет быть нужна.
2. **`pi-objectives-status`** (в каталоге live) показан как существующая панель «Current PI objectives» на Scale: она считается из событий, теперь с подсчётом committed / uncommitted. Отдельной плитки-числа у него нет.
3. **Диапазоны синтетики** (`src/synthetic/specs.ts`) я задал сам как правдоподобные значения для здоровой организации. Это иллюстрация, а не бенчмарк и не утверждение. На странице так и написано, целей и цвета у таких метрик нет. Примеры: availability 99.95 %, DoD compliance 94 %, PR throughput 18 в неделю на команду, eNPS-подобные опросы ~70 % favourable.
4. **SAFe Competency и DevOps Health Radar** сейчас — одна оценка по шкале 1–5 с квартальным рядом по командам. Радар по измерениям (7 компетенций SAFe, 4 аспекта × 16 под-измерений DevOps Health Radar) не делал: списков измерений нет в `content/`, а выдумывать их нельзя.
5. **Выключение живой метрики в Library** прячет её и из сигналов: иначе счётчик в шапке противоречил бы экрану. Тесты базовой линии считают все метрики, как и раньше, — Library влияет только на отображение.
6. **Sprint burndown / burn-up на уровне программы** суммируют текущие спринты всех Scrum-команд (каденс общий). Если выбрана команда — только её спринт. Время, когда задача добавлена в спринт, оценивается приближённо: момент создания в спринте или первая смена статуса внутри него (подписано под графиком).
7. **Свои симптомы** (SPEC §7 «пользователь может добавлять свои») в 3a не делал: этого не было в задаче. В Library есть только включение и выключение.

## ⚠ Нужно твоё решение

1. **Четыре метрики в каталоге помечены live, но не вычисляются:** `feature-lead-time`, `epic-lead-time`, `portfolio-wip`, `wsjf`. В реестре у них нет формулы, цели и бенчмарка, а придумывать их нельзя. Сейчас они видны в каталоге как «live · not computed yet» без плитки, тест фиксирует этот список. Варианты:
   - (а) Cowork готовит для них registry-метаданные (определение, формула, цель, бенчмарк), и я добавляю вычисление. Feature и Epic lead time считаются из уже существующих событий без изменений симулятора. Portfolio WIP требует уровня портфеля, а он пока заглушка. WSJF требует оценок cost of delay, которых в событиях нет;
   - (б) перевести их в каталоге в `synthetic`.
2. **Ошибка в статье pi-forecast (Monte Carlo).** В разобранном примере написано «≤ 5 недель примерно в 83 %, ≤ 6 — в 99 %». Точный расчёт (свёртка) даёт **81,2 %** и **98,0 %**, калькулятор на 10 000 прогонах — 80,9 % и 98,1 %. «≤ 4 недели ≈ 31 %», P50 = 5 и P85 = 6 верны. Предлагаю Cowork исправить на «about 81 %» и «about 98 %».
3. **Флаги из контента** видны на экранах и ждут решения:
   - cycle-time: «P85 / P50 above ~3» — практическая эвристика (калькулятор показывает отношение без порога);
   - say-do-ratio: коридор 80–90 % без исследовательского бенчмарка.
4. **Шкала 1–5** у SAFe Competency и DevOps Health Radar — моё допущение. Нужно подтверждение по первоисточнику.
5. **Дубликат источника:** `kersten-project-to-product` (из контента) и `kersten-p2p` (из реестра) — одна и та же книга. Оставил оба ключа, чтобы ничего не сломать. Можно свести к одному.

## Как проверить самому

- Catalog → фильтр Status = Synthetic → любая строка → переключатель «Show on the … tab» → вкладка: появилась пунктирная плитка SYNTHETIC с подписью «in production: …».
- Library → Export JSON → Reset → Import JSON: настройки вернулись.
- Learn → Tier 1 → Cycle Time / Say/Do / PI Forecast: калькулятор показывает разобранный пример из статьи; у остальных метрик — «Article coming».
- Diagnose → Flow → «Work gets stuck in review…»: шесть живых мини-плиток меняются вместе с часами симуляции.
- Scale: сверху шесть SAFe flow-метрик.
