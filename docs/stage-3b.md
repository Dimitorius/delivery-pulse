## Решения при реализации (на твой просмотр)

1. **Эпики в симуляторе.** На каждом PI Planning открываются 3 эпика. Закоммиченные фичи каждой команды делятся по приоритету на трети: первая треть → эпик 1, вторая → эпик 2, последняя треть и stretch → эпик 3. Так эпики естественно идут по WSJF, а WIP эпиков 1–3. Названия эпиков — из нового списка `PORTFOLIO_EPICS` в `src/sim/org.ts` (выдумал нейтральные).
2. **Мощность QA в review-bottleneck.** Первая версия только удлиняла ожидание. Throughput почти не падал, и дата Monte Carlo сдвигалась лишь на ~неделю. Теперь QA-проверка длится ×2.5 и ограничивает выпуск — это честная механика узкого места, и сдвиг даты заметен.
3. **Одновременно активен только один сценарий.** Сценарии действуют на всю программу, не на одну команду.
4. **Мобильная версия.** Кнопки Inject и Tour на телефоне скрыты (Pulse там только для чтения), баннер виден.

## ⚠ Нужно твоё решение

1. **Feature Lead Time считает только фичи, запланированные на PI Planning (под эпиком).** «Roadmap»-фичи, которые команда тянет вперёд без PI Planning, ждут в бэклоге до года. С ними P85 ≈ 200 дней, и плитка была бы красной из-за артефакта симулятора, а не поведения ART. В формулу добавлено «planned at PI Planning (under an epic)». Определение Cowork в остальном не тронуто. Согласен?
2. **WSJF-оценки следуют плановому порядку.** Симулятор не пересортировывает бэклог по WSJF: иначе пришлось бы менять основной поток случайностей и заново искать seed. На каждом PI Planning оценки (UBV, TC, RR|OE по шкале Фибоначчи) подбираются так, чтобы ранжирование примерно повторяло приоритет команд, с естественным шумом относительных оценок. Job size берётся из реальных story points фичи. Поэтому adherence 80–95 % — свойство модели «ART планирует по WSJF», а не открытие.
3. **Пары ≈ у новых метрик.** У Feature Lead Time и Portfolio WIP в черновиках не было флага или отметки `verified`, а тест реестра их требует. Я добавил флаги ⚠ (на сайте они видны как Caveat). Для Portfolio WIP ещё и пояснение: «SAFe Flow Load считает все элементы в работе на уровне, здесь — только эпики». Это моя формулировка — нужна сверка с первоисточником.
4. **Сигналы для 11 сценариев без файла симптома — мой выбор** (см. таблицу, `src/sim/scenarios.ts`). Когда Cowork напишет `content/symptoms/<id>.md`, тест автоматически возьмёт его early/confirming. Если механика их не сдвинет, тест покажет это красным.
5. **Критерий «раньше» не строгий:** не «каждый ранний раньше каждого подтверждающего», а «первый раньше первого и в среднем раньше». Строгий критерий противоречил бы самому файлу review-bottleneck: там сказано, что time-to-merge «rises together with pickup time». Отдельные ранние сигналы могут реагировать позже отдельных подтверждающих: у missed-dates aging-wip реагирует через 15.5 дня, say-do — через 10.
6. **Сила сценариев** (×5, 45 %, +60 ч и т. д.) — мои иллюстративные значения, подобранные так, чтобы эффект был виден за 1–3 недели симуляции. Это не бенчмарки.
7. **Уровни по измерениям на радарах** (база 3.4–3.6 ± разброс) — иллюстрация, как и прежняя одна оценка. Оговорки из файла показаны.
